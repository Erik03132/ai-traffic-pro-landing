# ADR-004 — Аналитика: Яндекс.Метрика, четыре цели, контракт имён

- **Дата:** 2026-11-02
- **Статус:** Accepted
- **Контекст задачи:** ROADMAP 0.1 (Метрика), блокер измерения эффекта редизайна

## Контекст

До этой правки на сайте не было аналитики вообще: эффект редизайна и правок
контента измерялся только числом заявок в Telegram. Это блокировало Фазу 0
(«Метрика с целями») и не позволяло отличить «стало лучше» от «стало хуже» при
просадке трафика.

Ограничения:

1. Сайт — статика на Cloudflare Pages, сборка в GitHub Actions. Номер счётчика
   не должен лежать в репозитории (меняется по окружениям, не является секретом,
   но и не контент).
2. Формы собирают персональные данные (имя, телефон/Telegram) — запись ввода
   (Webvisor) требует отдельной юридической проверки по 152-ФЗ.
3. Цели должны переживать рефакторинг компонентов: имя цели — внешний контракт
   с интерфейсом Метрики, его нельзя менять «по ходу».

## Решение

1. **Один компонент счётчика** — `src/components/Analytics.astro`, подключён в
   `Base.astro`. Номер счётчика — `PUBLIC_YM_COUNTER_ID` (build-time env).
   Пустое значение = компонент не рендерится, цели не отправляются.
2. **Одна точка отправки целей** — `reachGoal()` из `src/lib/analytics.ts`.
   Компоненты не знают, есть ли счётчик: без него вызов — no-op и `false`.
3. **Четыре цели с фиксированными именами** (контракт):
   `lead_submit`, `phone_click`, `chat_open`, `scroll_75`.
4. **Семантика целей:**
   - `lead_submit` — только успешный ответ API (не клик по кнопке): иначе цель
     считает валидационные ошибки и сетевые сбои.
   - `phone_click` — каждый клик по `tel:` (делегирование на `document`).
   - `chat_open` — один раз за страницу: важен факт интереса к чату.
   - `scroll_75` — один раз за страницу, только если страница прокручивается
     (запас ≥ 200 px), иначе «дочитал» ничего не значит.
5. **Webvisor выключен.** Включение — отдельное решение после проверки
   маскирования полей (152-ФЗ) и согласия в политике.

## Последствия

- Добавление цели = новая строка в `Goal` + вызов `reachGoal` + цель в интерфейсе
  Метрики + строка в таблице README. Тест `src/lib/analytics.test.ts` ловит
  поломку no-op-поведения и `once`.
- Счётчик не влияет на сборку: без переменной страницы собираются как раньше.
- Требуется действие человека: создать счётчик, задать 4 цели, добавить
  `PUBLIC_YM_COUNTER_ID` в Variables репозитория.

## Проверка

1. `npm test` — 5 тестов `analytics.test.ts` зелёные.
2. `npm run build` с `PUBLIC_YM_COUNTER_ID=00000000` — в `dist/index.html` есть
   `mc.yandex.ru/metrika/tag.js`, в HTML есть `ym(00000000, 'init'`.
3. Без переменной — ни `metrika`, ни `__ymCounterId` в HTML нет.
4. На проде: цель `test_goal` доходит до интерфейса Метрики (см. README).

## Инциденты при включении (02.11.2026) — читать перед правкой счётчика

Оба дефекта **не видны в HTML и не дают ошибок на глаз**: страница выглядит
правильно, счётчик «стоит», данных нет.

### 1. CSP блокировал загрузку tag.js

`Content-Security-Policy` из `public/_headers` разрешал только `'self'`.
Браузер блокировал `https://mc.yandex.ru/metrika/tag.js`, в консоли — CSP-ошибка,
в Метрике — ноль визитов. Исправлено: `mc.yandex.ru` добавлен в `script-src`,
`img-src` (пиксель `<noscript>`) и `connect-src`. Защита от регресса —
`tests/headers.test.js`.

### 2. `ssr: true` обрывал инициализацию

С опцией `ssr: true` (предназначена для SPA/SSR) tag.js загружается с кодом 200,
`window.Ya` появляется, но счётчик не регистрируется: `window.Ya._metrika.counters`
пуст, хиты на `/watch/<id>` не уходят, ошибок в консоли нет. Проверено на
изолированной странице: с `ssr: true` — 0 хитов, без него — регистрация
`"<id>:0"` и хит в `/watch/<id>`. Опция убрана; `ecommerce: 'dataLayer'` тоже
(данных ecommerce на сайте нет). Защита от регресса —
`tests/analytics-config.test.js`.

### Как проверять счётчик правильно

Не по наличию кода в HTML, а в браузере:

1. `window.Ya._metrika.counters` → должен содержать `"<id>:0"`.
2. В Network есть запросы `mc.yandex.ru/watch/<id>...`.
3. Для целей — запрос с параметром `goal=<идентификатор>` после действия.

### Объективная проверка через API Метрики (предпочтительно)

Проверки в браузере показывают, что хит **отправлен**, но не что он **записан**.
Внешний `curl` на `/watch/<id>` не доказывает ничего: несуществующий счётчик
отвечает так же (200, 43 байта, 1×1 GIF). Единственное доказательство —
данные из Stat API.

```bash
T=$(cat ~/.config/opencode/secrets/yandex-oauth.token)

# визиты и достижения целей за сегодня
curl -s -H "Authorization: OAuth $T" \
  'https://api-metrika.yandex.net/stat/v1/data?id=<COUNTER_ID>&date1=today&date2=today&metrics=ym:s:visits,ym:s:users,ym:s:goal<GOAL_ID>reaches'
```

Замечания по API:

- метрика достижения цели пишется **строчными**: `ym:s:goal<GOAL_ID>reaches`
  (с заглавной `Reaches` — ошибка `4002 Incorrectly specified metric`);
- список счётчиков: `/management/v1/counters`, цели: `/management/v1/counter/<id>/goals`;
- токен: OAuth-приложение типа «Для доступа к API или отладки», доступ
  `metrika:read`, Redirect URI `https://oauth.yandex.ru/verification_code`
  (токен показывается прямо на странице). Хранить в
  `~/.config/opencode/secrets/yandex-oauth.token`, права 600, в git не класть.

**Задержка отчётов.** Новый счётчик и первые визиты появляются в веб-интерфейсе
не мгновенно: агрегация идёт порциями (обычно 15–40 минут). «Нет данных» в
отчёте сразу после первого визита — это ещё не дефект; сначала Stat API.
