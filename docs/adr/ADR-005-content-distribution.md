# ADR-005 — Дистрибуция контента: реестр, очередь, адаптеры площадок

- **Дата:** 2026-11-16
- **Статус:** Accepted
- **Контекст задачи:** 11 статей в блоге, 5 постов в Telegram, ритм «пост раз в три дня»,
  следующая волна площадок — MAX, VK, Дзен, ОК

## Контекст

К 16.11.2026 контент и его распространение живут в двух несвязанных контурах.

**Контент** — `src/data/blog/*.ts` (11 статей, даты 09–16.11), обложки
`public/blog/*.jpg` (1200×630 + 1080×1080), посты для соцсетей —
`docs/distribution/posts/<slug>.post-N.md`.

**Публикация** — полуручная: `tools/tg-publish/send.py` → Worker `/api/tg/preview` →
черновик в личку владельцу → кнопка «Опубликовать» → `/api/tg/webhook` → канал.
Тексты постов пишутся руками под Telegram (переносы, `{{link}}`, подпись к фото).

Что уже работает в пользу автоматизации:

1. Публикация идёт через Worker, а не с локальной машины — кнопка и KV уже там.
2. В Worker есть cron (`0 7 * * *`) — планировщик не нужно поднимать с нуля.
3. UTM-контракт (`src/lib/utm.ts`, `buildLink` в Worker) — источник трафика
   различается по каналу без доработок.
4. Один материал уже даёт несколько постов (`post-1`, `post-2`) — запас
   публикаций больше числа статей.

Чего нет: единого реестра «что куда ушло», очереди с датами, RSS-ленты,
адаптеров площадок. Сегодня ответ на вопрос «эта статья уже была в VK?» —
только в голове владельца.

## Ограничения

1. Сайт статический (GitHub Pages), API — Worker. Планировщик может жить только
   на Worker: локальный `launchd` требует включённого Mac.
2. Статья в 1 500–2 000 слов и пост в соцсеть — разные жанры. Механическая
   нарезка статьи в пост даёт либо стену текста, либо голую ссылку.
3. Лимиты площадок различаются в разы: подпись к фото в Telegram — 1 024
   символа, текст сообщения — 4 096, пост VK — до 16 000, Дзен принимает
   только полный текст через RSS.
4. Автопост без просмотра — необратимое действие: удалить пост из чужой ленты
   нельзя, а опечатка видна всем подписчикам.
5. Контент — источник истины в git. Состояние публикаций, которое нельзя
   отревьюить в diff, через месяц превращается в необъяснимый KV-мусор.

## Проверенные факты о площадках (16.11.2026)

| Площадка | Программная публикация | Источник | Готовность |
|---|---|---|---|
| Telegram | Bot API, бот-админ канала, `sendPhoto`/`editMessageMedia` | код Worker, работает | ✅ работает |
| MAX | Bot API `POST https://platform-api2.max.ru/messages` — диалог, группа **и канал**; вложения `image`, `inline_keyboard`; лимит 2 сообщения/сек | `dev.max.ru/docs-api/methods/POST/messages` | ✅ API есть |
| VK | `wall.post` + загрузка фото в 3 шага (`photos.getWallUploadServer` → `save` → `wall.post`), есть родное `publish_date` | документация VK (требует проверки типа токена) | ⚠️ проверить права |
| Дзен | **API публикации нет.** Только трансляция RSS из Студии: домен подтверждён, ≥10 подписчиков, лента с того же домена | `dzen.ru/help/ru/website/rss-modify.html`, `site-to-channel.html` | ⛔ только RSS |
| ОК | `mediatopic.post`, нужны приложение, OAuth-сессия, права на контент | документация OK API (требует проверки) | ⚠️ дорого, отдача под вопросом |

Требования Дзена к ленте (по документации): RSS 2.0 + `content`, `dc`, `media`,
`atom`; в каждом элементе — `title`, `guid`, `pubDate`, `enclosure` (обложка),
`content:encoded` (полный текст), `link`, `description`; изображение ≥ 700 px
по ширине; при первой разметке — не менее 10 материалов; повторная проверка
ленты после отклонения за нарушения — через 6 месяцев.

## Решение

1. **Реестр дистрибуции — в git: `docs/distribution/registry.json`.**
   Элемент = одна публикация: `id` (`<slug>:post-N:<channel>` — канал в id,
   потому что статус у Telegram и VK независимый), `slug`, `post`, `channel`,
   `plannedAt`, `status` (`draft` — текст не написан / `queued` — текст есть и
   проходит лимиты / `approved` / `posted` / `failed` с причиной), `messageId`,
   `url`, `error`. Git — источник истины (ревью, история, откат);
   KV на Worker — зеркало для cron, обновляется `npm run dist:sync`.
   Реестр проходит гейт `npm run dist:check` в CI: ссылки на существующие
   статьи и файлы, уникальные id, известные статусы, тексты в пределах лимитов.

   **Поправка к решению (16.11.2026, этап 2):** зеркало в KV заменено
   манифестом на сайте. У Worker нет доступа к git, а тексты постов живут в
   репозитории, поэтому `/distribution/manifest.json` собирается на билде из
   реестра и файлов постов (см. `src/pages/distribution/manifest.json.ts`).
   Так источник истины остаётся один (git), копий текстов в KV нет, а cron
   читает готовый снимок очереди одним запросом в сутки. `dist:sync` не нужен.
2. **Текст поста принадлежит контенту, а не адаптеру.** `post-N.md` остаётся
   рядом со статьёй; адаптер только рендерит и проверяет лимиты. Один материал
   → N постов → M площадок.
3. **Ручной гейт остаётся по умолчанию.** Автоматизируем подготовку, доставку
   черновика, учёт и повторы; решение «в канал» — нажатие кнопки. Для площадки,
   которой доверяем, включается `auto: true` в конфиге канала — точечно.
4. **Один интерфейс адаптера:** `prepare(pub) → payload`, `send(payload) →
   {messageId, url}`, `edit(...)`. Общий объект публикации, рендерер на канал,
   лимиты в константах канала.
5. **Идемпотентность обязательна.** Ключ `pub:<channel>:<id>` пишется в KV
   **до** отправки в канал; повторный cron его видит и не постит. Ошибка
   площадки записывается как `failed` с причиной — тихий пропуск запрещён
   (HT-3: у отказа должно быть имя).
6. **Очередь двигает cron Worker.** Отдельный триггер проверяет «есть ли
   due-публикация на сегодня» и готовит черновики; расписание — данные
   (`plannedAt`), а не код.
7. **RSS — первый класс, а не побочный эффект.** `/rss.xml` с полным текстом:
   вход в Дзен, Яндекс и агрегаторы, а также единственный программный путь
   в Дзен вообще.

## Последствия

**Хорошо:** один ответ на «что где вышло»; новая площадка = один адаптер, а не
новый пайплайн; сбой канала не блокирует остальные; ритм публикаций задаётся
датой, а не памятью.

**Плохо:** появляется второй источник состояния (git + KV) — расходиться они
будут, поэтому `dist:sync` пишет в KV только из git, обратной синхронизации нет.
Плюс каждый адаптер надо поддерживать, когда площадка меняет API.

**Открытый хвост этапа 2:** кнопка «Опубликовать» пишет метку `pub:tg:<id>`
в KV, но статус в `registry.json` сам не меняется — его двигает человек
(`render.py --mark posted`). Пока это осознанно: git не может обновляться
из Worker. Когда расхождение начнёт мешать, добавляется `dist:pull` —
чтение меток из KV и запись в реестр одной командой.

**Явно не делаем:** пост на деплое сайта (деплой ≠ публикация, отменить нельзя);
универсальную CMS с ручным UI (4 адаптера и один JSON дешевле); копию текстов
постов в KV (только ссылки на git); авто-постинг во все каналы сразу без
проверки хотя бы одной площадки в бою.

## Открытые вопросы (закрыть до соответствующего этапа)

1. MAX: условия регистрации бота (юрлицо/ИП), нужен ли модерационный гейт.
2. VK: достаточно ли токена сообщества для `wall.post`, или нужен токен
   пользователя с `wall,photos`.
3. ОК: окупается ли поддержка приложения ради перепубликации.
4. Дзен: первая подача ленты — 10 материалов минимум; как поведёт себя лента
   при последующих обходах (guid стабилен, старые элементы не должны создавать
   дубли — проверяется по статистике Студии).
